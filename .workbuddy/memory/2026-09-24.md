## DeepSeek 5 项测试失败归因（10:32–10:37 批次）

排查入口：`web/data/runs.db`（runs 表按 created_at 取当天记录）→ 各 run 的 `result_dir/summary.json` + `results/web-<run_id>.log`。

### 1) DS_V4_P0 / DS_V4_P1 / DS_V4_P2：启动即失败，未发出任何请求
- 现象：exit_code=2，日志只有 `run_deepseek_v4.py: error: unrecognized arguments: DS_V4_P0`。
- 根因：`web/server.py` 第 503-504 行的 else 分支用**位置参数**传 `job["case"]`，而 `scripts/run_deepseek_v4.py` 只支持 `--model/--priority/--case/--list/--output-root`，没有位置参数。
- 附带缺陷：该 runner `--priority` 只有 P0/P1（CaseSpec 统计 P0=17、P1=7），而 `dsv4/cases.py` 里 `DS_V4_P2` 声明 priorities=("P2",)，**无对应可执行优先级**；`--case` 只认 `DS-V4-xx` 形式 ID，不认 `DS_V4_P0`。
- 潜在第二层坑：`latest_result()` 用 `RESULTS.glob(f"{name}-*")` 找结果目录，但 runner 输出目录是 `DEEPSEEK-V4-<ts>`，即使修好 argparse 也找不到 summary/report（需要加 aliases）。

### 2) DS_CONTRACT：5 项 → 4 通过 1 失败
- CONTRACT-01「身份与路由」failed：请求/响应 model 均为 `deepseek-flash`，但 `common/model_contracts.py` 的 deepseek profile 默认 `expected_model_tokens=("deepseek-v4",)`，且 `common/data/` 下**只有 glm.json，没有 deepseek.json** 覆盖 → 令牌不匹配。
- 其余 4 项通过：非法 temperature→400；SSE DONE 完整；tool_calls=1；reasoning_effort 三档 200 且 reasoning 1530/1684/2444 字符。

### 3) DS_V4_FINGERPRINT：6 项 → 3 通过 2 warning 1 failed，且无执行证据
- AUTH-01 warning：`tool_choice=required` 在 thinking 模式被拒，HTTP 400 `Thinking mode does not support this tool_choice`。
- AUTH-02 warning：`response_format.type=json_schema` 不可用，HTTP 400 `This response_format type is unavailable now`。
- AUTH-05 failed/not_evaluable：**测试脚本 bug** —— `authenticity.py:51` 把 `stream=True` 放进了 payload，而非 `req(payload, stream=True)` 第二参数，于是走非流式分支用 `r.json()` 解析 SSE → 解析失败 → b={} → DONE=None/content=0。属误报。
- `validation.json` 的 `evidence_present=false`：`authenticity.py` 不写 `requests.jsonl`，本批零证据 → 直接不准入（比单个用例失败更严重）。

### 结论
`admission_passed=false` 分别由「报告器 bug」「模型别名与期望令牌不一致」「Web→runner 参数契约断裂」造成，**都不是被测量模型本身的性能结论**。修复顺序建议：server.py 的 deepseek 分支加 `--case` + 结果目录别名 → authenticity.py 修 stream 调用并可写入 requests.jsonl → 统一 deepseek 模型别名（`deepseek-flash` vs `deepseek-v4-flash`）。
