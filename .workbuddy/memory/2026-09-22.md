### P0 缺陷（已代码级 + 运行时双重实证）
1. **`web/server.py:446` 引用 6 个从未定义的常量**：`ARXIVMATH_SCRIPT` / `DEEPSWE_SCRIPT` / `SWE_ATLAS_TW_SCRIPT` / `SWE_ATLAS_RF_SCRIPT` / `LEGAL_AGENT_BENCHMARK_SCRIPT` / `GLM_STREAM_RETEST_SCRIPT`。AST 检查确认模块级无定义（同名 `*_CASE` 常量存在 → 是漏写路径）。
   实证：`_execute_child({"test_kind":"arxivmath",...})` → `NameError: name 'ARXIVMATH_SCRIPT' is not defined`（deepswe / swe-atlas-tw / legal-agent-benchmark 同）。
   **杀伤半径**：`worker()` 只有 `try/finally`、**无 except**（全文件 68KB 仅 `:544` 一处 `except Exception`，且在 `script = ...` 之后）→ NameError 逃逸出线程 → **队列永久卡死，必须重启进程**。前端 `app.js:215` 的 `effectiveTestKind` 正好会解析出这 5 个 test_kind。
   注：这 5 个 runner 脚本（`scripts/run_arxivmath.py` 等）**本身是完整真实实现**，只是 Web 侧接线丢了。deepswe 需 `pier` CLI + git clone 官方仓库到 `data_cache/deepswe-official`；arxivmath 需 HF `datasets`。
2. **零鉴权 + 默认 `0.0.0.0:8085`**：`server.py` 中 Authorization/token/session/cookie 出现 0 次。同网段任何人可用你的 key 跑测试、读全部报告/日志/requests.jsonl、打包下载。路径穿越与命令注入已防护（resolve+父目录校验；Popen 列表 + shell=False + 白名单）。

### P1 缺陷
3. **空断言恒真**：`common/test_framework.py:validate_case(record, [])` → `passed=True`（对 HTTP500 + transport_error 也通过）；`validators.content()` / `tool_calls()` 无参调用恒真。与"HTTP 成功 != 案例通过"的承诺冲突。
4. **单 worker 串行 + 子进程无超时**；`cancel` 对 queued 任务只改 DB 状态（`:788`），不摘队列、无进程可杀 → 仍会启动并消耗额度。
5. **KVV 准入忽略 skipped**（`kvv/runner.py:117` 只看 exit_code/failed/errors）；且 `test_tokenization_groundtruth.py:83`（该套件**唯一** groundtruth oracle）被 `@pytest.mark.skip("skip, not pass")`，恰是 `SUITE_PATHS["k3_features_core"]` 成员。`test_thinking_effort.py` 另有 6 处 skip。
6. **authenticity 永远"未通过"**：其 summary 不含 `admission_passed` → finalizer 的 `original and not blocking` 恒为 False，6 探针全过也判 not_evaluable。

### P2
7. 指标口径跨引擎不一致：`k3perf/client.py:131` 把首 visible content 记为 ttft（对思考模型实为 TTFC）；TPOT basis 两引擎不同（visible vs 含 reasoning）→ 不可直接比较。
8. 重试策略不一致：volcperf/strictperf/gpt_image/dsv4/glm53 **无重试**，429 直接计失败，而 L*/C1 要求成功率≥0.99 → 一次限流即整体不通过；仅 k3perf 有 2× 尝试预算、moderation 有 3 次退避。
9. `moderation_test_project/build_report.py:29` 用 `len(v)==3` 判"结构完整"，生成器每组产 **5** 条 → 该指标恒 0（同文件 `:36` 又接受 `{3,5}`，自相矛盾）。
10. `vendor_verifier/verify_params.py:91-94` 任意异常（401/429/超时）都判"正确拒绝" = 假通过；`mmmu_pro_vision.py:160` 解析失败随机猜选项。
11. 死代码/双分叉：`vendor_verifier/utils.py` 整模块零调用；`common/{runner,case_model,case_schema,request_ids,legacy,verdict}.py` 无生产引用；`k3perf/awsb.py` 与根 `awsb.py` 双分叉；`scripts/run_.py` 文件名残缺；`SUITE_PATHS["k3_features_extensions"]` 无任何 KVV_CASES 引用（死配置）。
12. 四层契约（`common/architecture.md`）实际**只有 `scripts/run_temp_cases.py` 完整走通**；`mltest.result.v3` 是 finalizer 盖章字段，无 runner 原生产出 envelope（`artifacts.result_envelope()` 仅被测试引用）。
13. 核心路径零测试：`validate_case` 空断言、`suite.execute_manifest_case`、`runner.Runner`、`audit.redact`、verdict/case_model/case_schema/request_ids/legacy。
14. `results/` 只有 1 条真实记录（`CACHE_T0-20260921-171905`，mux.la/v1 + kimi-k3，20 请求全 client_error，成功率 0）→ 端到端链路近期基本没跑通，接线类问题正是靠这个才暴露。

### 建议修复顺序
① 补 5 个脚本路径常量 + 给 `worker()` 加 `except Exception` 兜底（唯一"点一下整站瘫痪"的问题）；② 收紧监听（默认 127.0.0.1 或加 Bearer）；③ 修空断言（空断言返回 not_evaluable + content/tool_calls 无参抛错 + 补测试）；④ KVV 把 skipped 纳入准入；⑤ authenticity 补 `admission_passed`；⑥ 统一重试与指标口径；⑦ 清死代码；⑧ 跑一次完整端到端回归。
