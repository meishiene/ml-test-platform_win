# 2026-09-17

## 跨项目排查：muxla-admin 线上发版被迁移守卫拦住

用户在本工作区（ml-test-platform）提问，实际涉及仓库 `/Users/yuhu/workspace/muxla-admin`
（pnpm workspace，NestJS API 在 `apps/api`，PG 库 `muxla_admin`，容器 `muxla-admin-muxla-ai` / `muxla-postgres`）。

**现象**：上线日志 `ERROR [TypeOrmModule] Unable to connect to the database. Retrying (6)...`
+ `Cannot retire admin_user.role while legacy key-merchant accounts remain: 2`。

**根因**：不是连不上库。`apps/api/src/database/migrations/1789086400000-retire-admin-user-role.ts:8-17`
的 fail-closed 守卫发现线上 `admin_user` 仍有 `role='key_merchant'` 的历史行（id=2），主动 throw。
`app.module.ts:57-67` 在 dataSourceFactory 里跑迁移，抛错被 NestJS 当作初始化失败重试（默认 10 次/3s，
本项目未覆盖 retryAttempts），容器 `restart: unless-stopped` → CrashLoop。
`migration-runner.ts:32` 用 `transaction='all'`，整批迁移一个事务，失败即全回滚（线上 schema 未被改动）。

**设计冲突（结论：这条迁移这一版不该发）**：
- plan `docs/superpowers/plans/2026-08-06-key-pool-removal.md:14,17` 要求 legacy key_merchant 行不删除/不迁移，
  且必须"仅可列表、不可登录"。
- 拒绝登录的判定全部依赖 DB 列 `admin_user.role`：`auth/auth.service.ts:85`、`auth/auth.service.ts:356-360`、
  `rbac/authorization-context.service.ts:23`。列一删 → 该账号变成"可登录、role 解析为 admin"。
- 因此守卫 fail-closed 是对的，问题在于删列的前提在真实数据上不成立。

**连带的真实缺陷（删列后必现）**：`auth/auth.service.ts:318-321` 的 `toListItemDto` 读 `user.role`，
实体已无 `@Column`，删列后恒为 `undefined` → `?? 'legacy'`；而 `AdminUserListItemDto`
（`packages/shared/src/index.ts:1210`）不含 `roles` 字段 → 前端 `admin-user-list.component.ts:97-101`
`canOperate()` 全部返回 false → 用户管理页所有行的编辑/停用/重置密码入口消失。

**测试盲区**：`auth/admin-users.service.spec.ts:301-315` 用内存假仓储（`users.rows`）模拟 legacy 行；
`test/retired-identities.postgres-spec.ts` 等 postgres 套件用 testcontainers 起全新 schema，
永远不会出现 legacy 行 —— 所以 CI 和本地都测不出这个守卫。

**给用户的方案对比**：A 保留列只停读（可发版，推荐）／B 迁移内先禁用 legacy 行再删列（违反 plan 且仍撞缺陷1）／
C 手工改线上库后发版（一次性，新环境会再炸）。用户尚未表态采用哪个，代码未改动。

## 续：muxla-admin 发版期「需要初始化什么数据」完整梳理

用户追问「发版时需要初始化哪些数据 / 一直起不起来」。已把启动期数据校验链路挖到底，结论如下。

**ml-test-platform 侧（当前工作区）先行排除**：启动零初始化。实测干净 `git clone` 后
`bash start.sh` 直接 HTTP 200 —— `web/server.py:300 initialize()` 自动 `mkdir` 出
`results/` 与 `web/data/runs.db` 并 `CREATE TABLE IF NOT EXISTS runs`。
`.gitignore` 忽略的 `web/data/*.db`、`results/*` 都不需要预置；`data/`、`data_cache/`、
`test_cases/` 均已入库。该仓库也无 Dockerfile/CI，不存在真正意义的「发版」。
唯一「缺数据」表现是 `moderation_test_project/*/cases.jsonl`（运行时由 `generate_cases.py` 生成，
缺失只导致用例数显示 0，不阻断启动）。

**muxla-admin 启动期数据校验链路（自上而下，任一不过即拒绝启动）**：

1. `app.module.ts:57-67` `dataSourceFactory` → `runControlledMigrations()`
   （`migration-runner.ts`，`transaction='all'`，先 `pg_try_advisory_lock('muxla-schema-migrations:v1')`）
2. `assertSupportedMigrationHistory()`（`migration-runner.ts:62-79`）——历史表 `muxla_schema_migrations`
   必须与 `SCHEMA_MIGRATIONS` 做**逐位比对**：含未知版本 → `Database history is newer than this application`；
   重复 → 同上；顺序错位 → `Database migration history has a gap or invalid order`
3. `DatabaseReadinessService.onModuleInit()`（`database-readiness.service.ts`）：
   - `applied === null` → `Database is not baselined. Run db:status and db:migrate before starting the API.`
   - 有未执行 → `Pending schema migrations: <names>. Run db:migrate explicitly.`
4. baseline 迁移 `1788739200000-existing-schema-baseline.ts`：空库按冻结 SQL 建 43 表；
   旧库取 `readSchemaCatalog` 比对，差异非空即 `Baseline refused; no business data changed (N differences)`

**迁移总数 58 个**（`apps/api/src/database/migrations/*.ts`），注册顺序在 `migrations/index.ts`。
带业务数据 fail-closed 守卫的迁移（线上数据不满足就 CrashLoop，发版前必须先清理）：
`1789086400000-retire-admin-user-role`（legacy key-merchant）、
`1789074000000-message-delivery-authorization`（空 legacy 凭据模板）、
`1789077600000-approval-rbac-authorization`（审批编码/角色映射冲突）、
`1789080000000-admin-external-identities`、`1789082400000-retire-sales-test-benefit-identity`、
`1789090000000-retire-admin-user-lark-projections`、`1789320000000-bananahub-platform-support`。

**其余需人工注入的初始化项**：`ADMIN_USERNAME`/`ADMIN_PASSWORD`（首次启动库内无用户时自动建）、
`rbac-bootstrap.service.ts`（自动）、`KEY_POOL_CREDENTIAL_ENCRYPTION_KEY`（AES-256-GCM，须与历史密文一致，
换密钥历史密文解不开）、`NEWAPI_LOG_DB_*`（外部日志库 ylapi-api-logs）。
生产部署包必须包含 `dist/database/migrations/baseline-20260907.json`（不能只拷 JS）。

**诊断要点（重要）**：`Unable to connect to the database. Retrying (N)...` 是**误导性表象** ——
dataSourceFactory 内任何 throw 都被 NestJS 包装成连接失败并重试 10×3s。真实错误在日志更上方。
发版顺序权威说明见 `docs/controlled-database-migrations.md` 第 3.5 条：**先跑结构迁移 → 再跑显式历史任务 →
最后启动新 API**；直接 `docker compose up -d --build` 会先停旧实例，新实例若迁移失败即全线中断。

**待确认未闭环**：用户始终未贴出线上真实报错，也未回答「是哪个项目」，本轮结论基于今早已知的守卫报错外推。
