## 结论：B1「多规格基线」与自定义性能参数的关系（代码级核查）

链路：前端 `#customEnabled` 勾选 → POST /api/runs 带 requests/concurrency
→ `web/server.py:915`（B1 不在 LOAD_PRESETS，不被预设校验拦截）
→ `web/server.py:447-449` 映射为 `--samples <请求数> --concurrency <并发>`
→ `volcperf/runner.py:429` samples 取用户值（非 quick 时不再被截断）
→ `volcperf/runner.py:434-435` 覆盖 case.concurrency
→ `volcperf/runner.py:96` `cycle(prompts)` 展开成 N 条请求计划。

关键事实：
- B1 默认 16 请求 / 并发 2（`volcperf/cases.py:40`，warmup=0、measured_seconds=0，故不受时长约束，请求数精确）。
- `volcperf/runner.py:30-37` B1 的 prompts = I1/I2/I3/I4 各取 4 条后交错；`--samples` 超过 16 时按 cycle 循环复用。
- **坑**：`volcperf/metrics.py:142-145` 的 `four_requests_per_size` 硬性要求每档 sent==4。设 100 请求 → 每档 25 → 该 check 必为 false → `admission_passed=False`。且 `error_rate` 要求 0 错误，30 并发下更易失败。
- 因此 B1 开自定义参数只适合当「4 档混排容量观察」，不能作为 B1 准入结论；baselines_by_dataset 的 TTFC 会变成 25 样本/档，语义与原基线不同。
- 界面里 B1 未标 `fixed_parameters`（只有 SIMPLE_LOAD / FULL_LOAD 标了 `web/server.py:173`），所以 UI 会放行自定义输入。

等价命令行：`python scripts/run_test.py B1 --samples 100 --concurrency 30`

## 结论：volcengine 协议下缓存能否命中（BATCH-f2300c6784944fc3 实测）

- 协议标识 `volcengine` 与 `openai` 共用同一份实现（`volcperf/protocols.py:27-28,38-39,51-58`），
  差别只在默认 base_url。本批 base_url 是第三方网关 `https://gate.jclxai.com/v1`（one-api 系，响应头 `x-oneapi-request-id` + `server: volcalb`）。
- **协议不阻止缓存**：上游 SSE usage 里确实返回 `prompt_tokens_details.cached_tokens`。
- **实测命中**（cached_tokens>0 / 每轮 50 条）：L1=2、L2=4、L3=3、L4=3、**L5=49**、O1=0。
  命中时 cached ≈ prompt_tokens - 1（整条 prompt 全额命中）。
- 命中条件是**同一条 dataset 记录被重复发送**（prompt 逐字节一致）：B1(17:48) 预热 I1–I4 各前 4 条 →
  L1/L2/L3/L4 各命中 2–4；L4(18:01) 发完 I4 前 50 条 → L5(18:02，间隔仅 2.1s) 命中 49/50。
- O1=0 是因为 `volcperf/runner.py:85` `record.workload(case.name == "O1")` 传了 fixed_output=True，
  TASK 文案与 L2 不同（同记录 prompt_tokens 12121 vs 12109），prompt 不一致 → 不命中。
- 公共前缀只有 181 字符（≈45 token，止于 `REQUEST_MARKER=`）：marker 是 `sha256("k3-admission-v1:<dataset>:<index>")`，
  唯一且位置极前 → 跨记录的前缀复用几乎不可能。
- **代码缺陷**：`volcperf/client.py:23-37` 的 `parse_event` 不读 `cached_tokens`，`reporting.py:9-16`
  的 REQUEST_COLUMNS 无缓存列 → 报告里完全看不到缓存（L5 98% 全量命中也不显示）。对照
  `k3perf`（`prompts.py` CACHE_PREFIX + `reporting.py` cache_ratio）与 `dsv4/glm53/awsb`（都读了 cached_tokens）。
- 附注：L5 全量命中缓存但 TTFT P90 仍 74.7s（全轮最差）→ 瓶颈在排队/解码吞吐，不在 prefill。

## 结论：BATCH-f2300c6784944fc3 性能指标分析（SIMPLE_LOAD 预设）

产物：`results/BATCH-f2300c6784944fc3/performance_analysis.md`

- 口径：SIMPLE_LOAD → L1–L5 各 50 请求**统一并发 30**（`web/server.py:74` 的 preset concurrency，
  不是 `cases.py` 里 50/40/25/15/8 的设计值），O1 并发 10；max_tokens L1–L5=1024 / O1=2048。
  因为走 preset，`--samples 50` 必然让 L1–L4 的 `sample_count` 失败（需 ≥100 / L4 ≥80）；
  未传 `--baseline-summary` 又必然让 L1–L4 的 `baseline_available` 失败 → 这两项是**预设/流程问题**，不是供应商问题。
- 性能主因（供应商侧）：
  1. TTFC p50 五轮全超（L1 11.83/限5、L2 11.94/限7、L3 17.47/限10、L4 22.96/限15、L5 48.97/限22）；
     `TTFT ≡ first_reasoning`，TTFC−TTFT 的"思考期"稳定 5.3–8.6s；TTFT 随输入线性劣化（7.5K 3.9s → 48K 15.2s）。
  2. **13 条零可见内容失败请求的形态完全一致：`reasoning_tokens == completion_tokens == max_tokens`、`finish_reason=length`**
     → 根因是 max_tokens=1024 对开启 thinking 的 K3 不够；推理占输出 38–52%。
     O1 用 2048 时截断率 4.2%（唯一达标），反向验证该判断。
  3. 截断率全线超 5% 门槛：L1 23.4% / L2 17.0% / L3 17.4% / L4 12.2% / L5 8.3%。
  4. **L4 vs L5 同负载（I4/48K、并发30、max_tokens 1024、50 样本）TTFT p50 恶化 2.74×、TTFC 2.13×、
     吞吐 48.4→19.4 RPM** → 服务端持续 48K 压力下排队衰减，不是随机抖动。这是本批最有价值的信号。
  5. 另有 1 次网关 504（O1-14）与 1 次中途断流（L5-9，`saw_done=false`，E2E 154.7s）。
- 唯一全绿指标是 TPOT P90（18.4–20.1 ms/token，门槛 60–90）→ 逐 token 速率没问题，问题在首字节时机与输出预算。
- 复测建议：max_tokens ≥2048 或降 reasoning_effort 后重跑；改用 FULL_LOAD（samples=100/concurrency=50）；
  先跑 B1 生成 baselines_by_dataset 再带 `--baseline-summary` 跑 L1–L4。

## 结论：上游网关日志交叉分析（BATCH-f2300c6784944fc3，修正了 L5 归因）

产物：`results/BATCH-f2300c6784944fc3/upstream_log_analysis.md` + `upstream_logs/{page1..4,merged,aligned,decomposed}.json`

- **拉取方式**：`GET https://gate.jclxai.com/api/log/self?p=N&page_size=100&type=0&start_timestamp=&end_timestamp=`，
  `Authorization: Bearer <dashboard JWT>`。本次 `total=305`（300 正式 + 5 次连通性探测），4 页取全。
  ⚠️ 该 JWT 有效期仅约 15 分钟（`exp-nbf=905s`），必须先分页兜底再分析。
- **字段语义（关键，易读错）**：`created_at` = **完成时刻**（不是开始）；`use_time` = 上游段耗时秒数（不含网关排队）；
  `other.frt` = 上游首响应毫秒；`other.cache_tokens`；`other.stream_status{status,end_reason}`；
  `other.upstream_model_name=kimi-k3`（下游名 `kimi-k3-hybrid`，`is_model_mapped=true`）；
  `request_conversion=["OpenAI Compatible"]`。`created_at - use_time` ≈ 客户端 `started_epoch`（±1s）。
- **对齐方法**：用 `prompt_tokens` + `completion_tokens` + 完成时刻（±3s）三重匹配 → 290/300，残差 p50 0.45s。
  不要用 started_epoch 匹配（并发 30 时同秒发起的请求会互相串位）。
- **三段分解（客户端首个 SSE）**：① 客户端发出→网关转发上游（排队）/ ② 上游 frt / ③ 回传。
  L1 0.05/3.19/0.66；L2 2.55/4.53/0.26；L3 2.25/7.79/0.51；L4 6.21/12.46/0.58；
  **L5 33.13/5.22/1.22（p90 排队 51s、max 85s）**；O1 −0.17/3.23/0.30。
- **结论修正**：L4→L5 的 2.74× 客户端劣化 **100% 来自网关排队段①**，不是上游模型退化 ——
  L5 缓存命中 41/41，上游 frt p50 5.22s 比 L4 的 12.46s 快 2.4×。缓存收益被排队吃掉还倒亏 27s。
  ③ 回传恒为 0.26–1.22s，非瓶颈。② 上游 frt 随输入线性：7.5K 3.2s / 12K 4.5s / 24K 7.8s / 48K 12.5s。
- **网关看板陷阱**：`use_time` 只覆盖上游段，网关后台把 L5 显示成"14s"，客户端实际 50s → 用网关看板做 SLA 会系统性低估。
- **计费公式（305/305 验证）**：`quota = (prompt − 0.9×cache + 5×completion) × model_ratio(5)`，`USD = quota/500000`
  （即 $10/M 输入、$50/M 输出）。本批实付 $63.68（含缓存折扣，省 $24.17/27.5%），
  但只换到 107,754 可见 token ≈ **$582/百万可见 token**（推理占输出 38–52% 且全额计费）。
  13 条零可见内容请求照常扣费 $2.40。
- **未闭环**：L5-9 客户端断流（485 SSE 事件、无 done）在上游日志中无对应记录；可用 `type=1/2/3` 再拉错误日志补齐。
  O1-14 的 504 在上游侧对应 `context canceled / client_gone`（use_time 65s，起止 18:05:20→18:06:25）。
