## 10:2x 复核「计费不准是不是因为截断」——用直连原始记录证伪

用户提问：i-token.ai 上"中转关不掉 thinking + max_tokens 小 → 没思考完就终止 → output_tokens 跟随 max_tokens"，
计费不准是不是这个原因。

取证源：`fable5_direct/out/run-20261008-191127/requests.jsonl`（91 条，76 条 200）逐条重算。

### 结论：用户描述的链**方向反了**——截断不是成因，别当因果
1. `ot == mt` 命中 **38/70**（256 档 23/36=64%、512 档 10/15=67%、1024 档 4/15=27%、2048/4096 档 0/1、0/2）。
2. **命中者 stop_reason = `end_turn` 34 条 + `tool_use` 3 条 + `max_tokens` 仅 1 条**。若主因是"思考没完被砍"，
   应大面积出现 `max_tokens`；真情截断只有 E19（`mt=16`，正文 1..16 被砍，回显 `max_tokens`）。
3. **13 条账目自相矛盾**（最硬）：`output_tokens − thinking_tokens = 1`，账目只留 1 token 给可见正文，
   而正文 12–183 字符且 `stop_reason=end_turn`。例：C12 `mt=256/ot=256/think=255` 正文 183 字符
   （`37 × 83 = 3071 **计算过程：**…`）；B15 `mt=512/ot=512/think=511` 正文 97 字符；B10 正文 83 字符英文。
   → 可见正文单独就已超过"留给它的 1 token"，上报值不可能是实测。
4. 首轮受控 A/B：同一提示「只回复 OK」，只改上限 → 64 得 `ot=64/think=63`、100 得 `ot=100/think=99`，正文完全相同
   → 账目随上限线性变化，不随内容变化。
5. 也存在"既非上限也非实测"的第三类值（B05 `1024→591/think=521` 差 70、B08 `649/440` 差 209）→ 无口径。

### 正确的因果
- **计费不准 ← 上报口径 = `max_tokens` 的函数**（推导/夹取），与真实生成量无关。
- **"thinking 关不掉"（71/76 响应带思考块，含显式 `disabled` 请求）是放大器，不是成因**：它保证预算总被填满，
  于是小上限既不省钱（账单贴上限）又可能真丢答案（E19），但解释不了那 34 条 `end_turn` 的假账。
- 独立的一条资金风险：**按下单 `max_tokens` 预扣**（`need quota` ≡ `max_tokens × $50/1M`：32000→$1.600080、
  500000→$25.000080、≈260→$0.012986），与真实生成量无关。**没有账单侧证据**，故"是否退还差额"未验证。

### 发现的缺口（未动代码）
- `fable5/` 现有 78 条里**没有**"用量可信性"用例（`fable5_direct/REPORT-fable5-itoken-relay` 早已建议：
  同提示 `max_tokens=M` vs `2M`，`output_tokens` 随上限变化即 R2 红线）。现只有 E19（真截断）、C13（字段完整性）。
- 已把成因结论回填 `MEMORY.md` 的 i-token 条目。

### 设计要点（值得记住的）
- **两个正交轴**：U 系列（用量真实性）只看响应内账目自洽性，不需要余额；B 系列（计费口径）
  只看前后余额差分。**只测其一会让「按下单上限扣款」与「伪造 usage」互相顶罪**——两个缺陷
  的症状都是「`output_tokens` 跟着 `max_tokens` 走」，但成因与修法完全不同。
- **B01 用三点双因子标定**：A=(小上限,长答案) B=(大上限,长答案) C=(大上限,短答案)；
  A→B 只改上限、C→B 只改内容。否则两个因子互相污染（首版就是三点配错，内容因子被上限因子吃掉）。
- **余额 oracle 三层降级**：`/dashboard/billing/{subscription,usage}` → 故意超额下单读 403 文案
  `remain quota` → 都不可得则计费类 `blocked`（缺取证能力 ≠ 通道有问题）。
- **判据纪律**：只有「贴上限 **且** 自称 `end_turn`」才是红线；贴上限但如实回显
  `stop_reason=max_tokens` 只算真截断（warning）。这条直接来自复核结论（38 条贴上限里 34 条 end_turn）。
- **blocked 收口**：401/403/429 或文案含额度/权限特征 → `blocked` 并写自解释理由。

### 三个真实 bug（都是自检发现的，不是用户报的）
1. **分辨率写死 $0.005**：精确的 403 oracle（$1e-6）被白白限制在分位，B01 全程误报「分辨率不足」
   而永远判不出红线。→ 分辨率随 oracle 走（`ORACLE_RESOLUTION`）。
2. **B04 冤枉通道**：余额**低于本次**冻结额时被拒属正常预扣检查，原实现一律判 failed
   「冻结未释放」。→ 加 `balance >= reserve(tiny)` 前置条件，否则 `blocked`。
3. **U02 假 failed**：长答案被上限截断时正文本身不完整，「条目数下界」不再成立。→ 加截断保护。

### 端到端验证（本地 mock，未打真实接口）

4. **落库相对路径统一 `as_posix()`**（`_portable_path()`）：原 `str(path.relative_to(ROOT))` 在 Windows 存成反斜杠，跨平台拷贝结果库即失效。
